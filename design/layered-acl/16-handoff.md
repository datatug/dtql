# Corpus implementation handoff — gated, not dispatched

Read [work packages](12-work-packages.md), [contract completion](15-contract-completion.md), [acceptance](11-acceptance.md) and [schemas](contracts/README.md) together. The user approved A1 suggestions, then requested this plan and another independent review. No package is authorized to begin MVP implementation until the resulting human checkpoint. Each package below is intended to become one independently reviewable worktree/PR, split a/b where dependency isolation is useful.

## Contract ownership and gate sequence

C1 policy + C2 wire + C3 identity + C4 evaluation/evidence + C5 revisions/publication + C6 query/write profile + C7 execution-route masks are versioned together in the DTQL packet. JSON Schema handles structural validation; semantic obligations are separately enumerated. Public Go DTOs live in DALgo `access/contract`; core assessment/evidence in `access`, no reverse import. TypeScript wire types are generated/checked from the same schema at implementation time, not hand-maintained parallel enums. Runtime validators still perform semantic checks. Runtime external-schema fetches are forbidden.

G0: human accepts reviewed plan and frozen contract digest. G1: WP0 verified current baseline and WP1 schema/fixture distribution pass. G2: WP2 stable additive API and legacy differential tests pass; WP3 may then change enforcement internals. G3: direct InGitDB secured adapter passes private evidence/CAS/crash gates. G4: OpenVaultDB and driver pass transport/owner bypass tests. G5: DataTug daemon + UI pass integrated contract tests. G6: actual T01–T21 and V01–V08 pass; publish provider-first releases and owner docs. A prototype or unit-only pass cannot satisfy a later gate.

A contract contradiction discovered during implementation stops only affected packages. Return a concrete failing vector and proposed contract patch to the design owner; do not silently fork behavior or weaken enforcement. Unaffected storage/UI work against fixed fixtures may continue. Unsupported reference capability is a release blocker, not an E2E skip. Additional nonreference adapters may remain explicitly unsupported.

## Start versus completion dependencies

WP4a/WP5a/WP7a may start after WP1 with fixed JSON fixtures and storage/transport doubles. WP4a cannot merge as complete until WP2a's real strict decoder and WP2b provider/caller interfaces replace doubles and all store validation tests rerun. WP5a likewise completes only after WP2a DTOs and WP2b owner capability/provider interfaces integrate and its HTTP tests rerun with the real shared package. No copied decoder/DTO implementation may survive that gate. WP7a can complete UI fixtures after WP1, but live integration is exclusively WP7b. WP4b's G3 result depends on WP3, not on a circular preexisting G3 release. WP0 records exact module commits for these completion edges.

## Exact ownership of semantic checks

- DTQL spec fixture owner: syntax/closed schemas, code taxonomy, C7 masks, operation discriminator/action correspondence, sample reducers, ID reference integrity and canonicalization examples.
- DALgo owner: hierarchy/bindings/predicates/fields, typed realm mapping adapter, class gates, required evidence, final candidate and multiple-policy assessments. Adapter conformance must use those functions.
- Storage owner: complete evidence, revision token coverage, transaction lock/CAS/all-or-none, atomic generation publication and committed recovery, source-name normalization.
- HTTP owner: authentication/delegation, capabilities and owner routing, disclosure, bounded body/deadlines and errors, no raw query/procedure fallback.
- DataTug owner: own server enforcement, faithful display/edit/round-trip, stale/sampled/hypothetical states. Browser permissions are hints only.

Each PR includes contract digest, prerequisite package commits/versions, touched surface, failure behavior, exact focused tests run, uncovered capabilities, and a link to its acceptance rows. A package is not done with only generated types or happy-path demos.

## Release and dependency waves

1. Publish reviewed DTQL specification artifact and DALgo additive APIs/validators with legacy tests; no downstream ACL enablement yet.
2. Publish InGitDB config nested-module change, then secured dalgo2ingitdb; verify module graph, no permanent local replaces.
3. Publish OVDB server/core and HTTP driver as a coordinated compatibility wave. Server advertises A2 capabilities; old servers fail protected client negotiation closed. Legacy ACL-disabled routes retain documented behavior.
4. Pin DataTug daemon once to verified providers, then browser client contract support. Do not infer remote ACL support from product version alone.
5. Run pinned full E2E and release owner docs/profile declaration. Enable ACL only after complete policies, identity mapping, manager and required capability verification; never deploy an empty enabled set or auto-disable on rollback.

Rollback of a component to a version lacking the enabled profile must refuse the mount, not serve unrestricted. Policy generation rollback is an authorized new revision through the owner control plane, not a client option to use cached decisions. Operational deployment tooling is reused; no new orchestration service.
